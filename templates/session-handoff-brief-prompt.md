# 單字「換」會話交接 Prompt 範本（Claude Code／Antigravity／Codex）

> **對應規範**：[`docs/long-chat-session-handoff-spec.md`](../docs/long-chat-session-handoff-spec.md)（第 3 節生命週期介面、第 3.3 節命名、第 3.4 節 Brief）。
> **來源與查證日期**：流程取自 `littlehole2025/claude-saver` commit `434750eb61510db40d567617862800f4fde2f65c` 的 `skills/handoff/SKILL.md`（2026-11-02 開啟比對）。各平台的工具名稱是否存在，見下方「各環境可用性」。
> **這份範本拿來做什麼**：複製第 2 節的 Prompt 到你的 skill、`AGENTS.md` 或自訂指令，使用者只打「換」就能得到一份可貼進新對話的交接 brief；能自動建立與封存的環境會自動做，不能的就降級成貼上。

---

## 1. 使用方式（三步）

1. 複製第 2 節對應環境的 Prompt 區塊，貼進該環境的指令檔（Claude Code：`SKILL.md` 或 `AGENTS.md`；Antigravity／Codex：各自的專案指令檔）。
2. 不需要改任何變數：`{{…}}` 是**執行當下由 Agent 填入**的欄位，不是你要預先改的設定。第 3 節是 Agent 該填的欄位說明。
3. 每次交接完成後，用第 5 節的檢查清單自檢；任何一項不成立就不要封存舊對話。

本範本**不依賴本 repo 的任何工具**，複製到別的專案可直接使用。

## 各環境可用性（先看這裡）

| 環境 | 自動建立新對話 | 自動封存舊對話 | 說明 |
| :--- | :--- | :--- | :--- |
| Claude 桌面版（Code 分頁） | 原作 skill 使用 `start_session` | 原作 skill 使用 `archive_session` | 這兩個工具名稱**官方文件查無，未驗證**，只出現在原作；工具清單裡沒有就走降級 |
| Antigravity | 本 repo 紀錄有 `agentapi new-conversation` | 本 repo 紀錄有 `UpdateConversationAnnotations` | **未對照廠商文件**，細節見 `docs/agent-dispatch.md`；不確定就走降級 |
| Claude Code 純終端機 | 無 | 無 | 官方做法是改名後 `/clear`，之後 `/resume` 回舊對話 |
| Codex | 未驗證 | 未驗證 | 一律走降級（貼上） |

降級（貼上）永遠可用：產出完整 brief，請使用者自己開新對話並貼入；**舊對話不動**。

## 2. Prompt 區塊（複製這裡）

### 2.1 通用核心（三個環境都要有）

```text
當使用者只輸入「換」、「開新」、"new" 或 "handoff"（單獨一個字，不含其他需求），直接執行交接，不要再問一次要不要換。

步驟：
1. 取得目前對話名稱 {{CURRENT_TITLE}}（工具取不到時，向使用者要，或用「對話」當名稱）。
2. 依「命名規則」算出 {{NEW_TITLE}}：取名稱最後一個連續數字加 1，其餘照抄；沒有數字就在最後加「-2」；保留前導零的位數。不要另取新名字。
3. 依「四段式 Brief」整理 {{BRIEF}}。每一段都要能獨立閱讀，不可寫「如上所述」「同前」這類要回頭看的字。
4. 若本環境有建立新對話的工具：用 {{NEW_TITLE}} 與 {{BRIEF}} 建立，並檢查工具回傳確認新對話真的存在。
5. 只有在第 4 步確認成功後，才封存目前對話。建立失敗、被拒絕、或無法確認時：不要封存，用一句話告訴使用者原因，並把 {{BRIEF}} 完整輸出讓使用者貼到新對話。
6. 本環境沒有建立新對話的工具時：直接輸出 {{BRIEF}}，並說明「這裡無法自動開新對話，請自己開一個並貼入」。

使用者是在被提示「對話很長、要不要開新對話」之後提出新需求時：先給兩個選項（開新對話／在這裡做）；選「在這裡做」就不開、不封存；選「開新對話」才做第 4、5 步，且 {{BRIEF}} 要多附一行「使用者的新需求：{{NEW_REQUEST}}」。
```

### 2.2 Claude Code（桌面版 Code 分頁）加掛

```text
本環境若有 get_session、start_session、archive_session 工具：
- 步驟 1 用 get_session（session 傳 "self"）取名稱。
- 步驟 4 用 start_session：context 設 "fresh"，title 用 {{NEW_TITLE}}，brief 用 {{BRIEF}}。
- 步驟 5 用 archive_session（session 傳 "self"）。
若工具清單裡沒有這三個工具（例如終端機 CLI），走步驟 6，並補一句：可先 /rename 目前對話再 /clear，之後用 /resume 回來。
```

### 2.3 Antigravity 加掛

```text
本環境若可呼叫 Antigravity 的對話介面：
- 步驟 4 建立頂層新對話，標題用 {{NEW_TITLE}}，第一則訊息用 {{BRIEF}}。具體指令與參數請查你所用版本的文件；找不到就走步驟 6。
- 步驟 5 把目前對話標記為封存，且必須保留原有標題與其他標註（不要覆寫）。
任何一步的回傳不是明確成功，就視為失敗，不要封存。
```

### 2.4 Codex 加掛

```text
本環境一律走步驟 6：輸出 {{BRIEF}}，請使用者開新的 Codex 會話並貼入。不要宣稱已封存或已建立新會話。
```

## 3. 變數說明（Agent 執行當下填入）

| 變數 | 內容 | 缺值時 |
| :--- | :--- | :--- |
| `{{CURRENT_TITLE}}` | 目前對話名稱 | 向使用者要；仍沒有就用「對話」 |
| `{{NEW_TITLE}}` | 依第 4 節規則算出的新名稱 | 不可留空 |
| `{{BRIEF}}` | 第 5 節四段式內容 | 不可留空；任一段沒有內容就寫「無」，不可省略該段 |
| `{{NEW_REQUEST}}` | 使用者剛提出的新需求原文 | 只在「提示後選開新對話」時使用 |

交接前自檢：輸出的文字裡不應再出現 `{{` 或 `}}`。

## 4. 會話命名規則

取名稱**最後一個連續數字**加 1，其餘字元照抄；沒有數字就在最後加 `-2`；數字前導零要保留位數。

| 舊名稱 → 新名稱 | 說明 |
| :--- | :--- |
| `對話-3` → `對話-4` | 一般情況 |
| `Yoto 網站 9` → `Yoto 網站 10` | 進位 |
| `SEO 調整` → `SEO 調整-2` | 沒有數字 |
| `專案-009` → `專案-010` | 保留前導零 |
| `v2 專案-3` → `v2 專案-4` | 只動最後一個數字 |

（上表五組都已用規範工具的 `title` 子命令實際算過，且有測試逐筆驗證。）

限制：名稱結尾若本來就是年份或版本號（「報告 2025」），會被當成流水號加 1。這類名稱請先在後面另加流水號。

## 5. 四段式 Brief 格式

把下面整段（含標題）填好後，作為新對話的第一則訊息或 `brief`。段落順序固定，每段至少一行，沒有內容就寫「無」。

```text
# 交接：{{NEW_TITLE}}（接續自 {{CURRENT_TITLE}}）

## 1. 已完工項目
- {{做完了什麼}}｜commit {{SHA 前 7 碼以上}}｜PR {{編號或「無」}}｜檔案：{{路徑}}

## 2. 未完工與卡點
- {{還沒做完的事}}｜卡在：{{原因}}｜已嘗試：{{做過什麼}}

## 3. 下一步待辦
1. {{第一件該做的事，動詞開頭，可直接執行}}
2. {{第二件}}

## 4. 環境偏好與全域約束
- 回覆語言與風格：{{例如 繁體中文、先結論後細節}}
- 專案硬規則：{{例如 測試綠了才能 commit、不可 push main}}
- 環境：{{作業系統、工作目錄、需要的指令}}
```

填寫規則：

- 第 1 段的 SHA 要用實際指令取得（例如 `git log --oneline -n 5`），不可憑記憶；沒有 commit 就寫「無 commit」。
- 第 2 段的「卡在」要寫成新對話的人讀得懂的原因，不可只寫「有問題」。
- 第 3 段每一項都要能直接動手，不寫「繼續處理」這種空話。
- 第 4 段只放會影響新對話行為的約束；不要貼機密、token、帳號、家目錄真實路徑。
- 全文不得出現「如上所述」「見前文」「同上」。

### 填好的例子（假資料）

```text
# 交接：結帳流程-4（接續自 結帳流程-3）

## 1. 已完工項目
- 新增優惠碼欄位驗證｜commit a1b2c3d｜PR 無｜檔案：src/checkout/coupon.ts、tests/coupon.test.ts

## 2. 未完工與卡點
- 運費計算尚未支援離島｜卡在：物流商 API 沒有離島代碼表｜已嘗試：查官方文件，只有本島區碼

## 3. 下一步待辦
1. 向物流商取得離島代碼表，補進 src/checkout/shipping.ts
2. 為離島情境新增兩個測試

## 4. 環境偏好與全域約束
- 回覆語言與風格：繁體中文，先結論後細節
- 專案硬規則：測試全綠才能 commit；不可直接推 main
- 環境：Windows 11，工作目錄為專案根目錄，測試指令 npm test
```

## 6. 交接前檢查清單

- [ ] 使用者輸入的是單獨的「換」類觸發詞，而不是夾帶其他需求
- [ ] `{{NEW_TITLE}}` 是依第 4 節規則算出的，不是自創名稱
- [ ] Brief 四段都在，沒有內容的段落寫「無」
- [ ] Brief 內沒有「如上所述」類字眼，也沒有殘留的 `{{`
- [ ] 第 1 段的 SHA 是實際查到的
- [ ] 建立新對話後，**看到回傳成功**才封存舊對話
- [ ] 任何一步失敗：舊對話沒有被封存，使用者拿到完整 brief
- [ ] 沒有貼入機密或真實帳號路徑
