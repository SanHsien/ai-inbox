# 需求解壓縮與名詞規格化提示詞範本

> 來源：`notes/2026-10-26-ai-freelance-certainty-pricing-and-dod-spec.md`（任務 `T-20261026-32`）。核心觀點（作者宣稱，原影片為 Debug 土撥鼠〈AI 199 元做網站？〉）：客戶報的是「名詞」（會員、電商、AI 客服），名詞是一個壓縮檔，裡面包著沒說出口的功能邊界、資料欄位與例外處理；對名詞直接報價，等於還沒拆開壓縮檔就先簽字。本範本把「拆壓縮檔」變成一套可重複執行的三層提示詞結構。

---

## 1. 三層解壓縮框架

```text
┌─────────────────────────────────────────────────────────────────┐
│ 名詞（客戶說的話）                                                  │
│ 例：「我要一個會員系統」                                             │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 第一層：功能邊界（Scope）
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│ 這個名詞實際要做哪些事、不做哪些事                                     │
│ 例：登入/註冊、忘記密碼、會員等級 —— 但「不含」第三方登入、不含點數商城    │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 第二層：資料模型欄位（Data Model）
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│ 每個功能背後要存什麼欄位、欄位的型別與必填/選填                        │
│ 例：member(id, email, password_hash, level, created_at, ...)      │
└───────────────────────────┬─────────────────────────────────────┘
                            │ 第三層：邊界異常處理（Edge Cases）
                            ▼
┌─────────────────────────────────────────────────────────────────┐
│ 每個功能的「如果…會怎樣」                                             │
│ 例：email 重複註冊？密碼重設連結過期？帳號被停用後還能登入嗎？          │
└─────────────────────────────────────────────────────────────────┘
                            │
                            ▼
              第一版 Single-file HTML 確定性原型
          （把以上三層變成客戶能點、能看、能挑錯的畫面）
```

**為什麼是這三層、且順序不能換**：
- 不先定 Scope 就去設計資料欄位，會把「本次不做」的功能也建了表，白做工。
- 不先定資料欄位就去想異常處理，異常會講不清楚是哪個欄位出問題（例如「email 重複」要先確定 email 是不是唯一鍵）。
- 三層都定了才做原型，原型才會是「這份規格的畫面版」，不是另一份憑空想像的 UI。

## 2. 解壓縮提示詞（複製後填入 `{{ }}`）

```text
你是需求分析師。客戶給的名詞是：「{{客戶原話，逐字抄，不要先幫他潤飾}}」。

請依下列三層結構解壓縮，每一層都要具體到「可以直接變成 DoD」的程度，
不要用「處理相關邏輯」「進行必要的驗證」這種空話：

【第一層：功能邊界】
1. 列出這個名詞下，本次「要做」的具體功能，每項一句話講清楚輸入與輸出。
2. 列出「Non-Goals（本次不做）」：常被誤認為包含在這個名詞裡、但本次明確不做的項目。
   （這一步最重要：寫出「電商系統」通常包含但這次不做的東西，例如多倉庫庫存、
   跨境金流、優惠券疊加規則——沒寫出來的，日後客戶會認為「本來就該有」。）

【第二層：資料模型欄位】
針對第一層列出的每個「要做」功能，列出對應的資料表／欄位草案：
- 欄位名稱、型別、必填/選填、預設值
- 哪些欄位之間有唯一性或關聯限制（例：email 唯一、訂單必屬於一個會員）

【第三層：邊界異常處理】
針對第二層每個欄位或每個功能，至少列 2 個「如果…會怎樣」的情境與處理方式：
- 衝突情境（重複、過期、超出範圍）
- 權限情境（誰能看、誰能改、未登入會怎樣）
- 外部依賴失敗情境（第三方 API 掛掉、金流逾時）

【輸出格式】
依上述三層分段列出；第一層的 Non-Goals 必須單獨列一個子清單，不要跟「要做」混在一起。
```

## 3. 第一版 Single-file HTML 確定性原型代碼結構

拆完三層後，把它變成客戶能親手點的原型，不是文字規格書。原型只示範「畫面與流程」，不接真實後端：

```text
single_file_prototype.html
├── <style>                    固定於同一檔案內，不外連樣式表
├── <body>
│   ├── #non-goals-banner      畫面上方常駐顯示本次 Non-Goals（避免客戶看了原型又加需求）
│   ├── #screen-list           每個「要做」功能對應一個畫面區塊，用 Tab 或錨點切換
│   │     └── 每個畫面內的表單欄位，命名直接對應第二層的資料模型欄位
│   └── #edge-case-demo        用假資料示範第三層列出的至少一個邊界情境
│         （例：故意示範「email 重複註冊」會跳出什麼提示）
└── <script>                   全部 inline，不讀外部 API；資料用記憶體內的假陣列模擬
```

**鐵律**：原型裡出現的每一個表單欄位，都必須能對回第二層的資料模型；原型裡沒有出現的欄位，不在這次報價範圍——這樣簽約時，原型本身就是範圍證據。

## 4. 反例對照：壞的解壓縮 vs. 好的解壓縮

| 層級 | ❌ 壞範例（空泛，等於沒拆） | ✅ 好範例（具體、可驗收） |
| :--- | :--- | :--- |
| 功能邊界 | 「做會員登入相關功能」 | 「Email+密碼註冊、Email+密碼登入、忘記密碼寄送重設連結（24 小時內有效）；**不含** 第三方 OAuth 登入、**不含** 雙因素驗證」 |
| 資料模型 | 「會員資料表包含基本資訊」 | 「`member(id INT PK, email VARCHAR UNIQUE NOT NULL, password_hash VARCHAR NOT NULL, level ENUM('free','paid') DEFAULT 'free', created_at DATETIME)`」 |
| 異常處理 | 「做好錯誤處理就好」 | 「註冊時 email 已存在 → 回傳 409 並顯示『此信箱已註冊，請改用忘記密碼』；重設連結超過 24 小時 → 顯示『連結已過期，請重新申請』並讓使用者重新觸發寄信」 |
| Non-Goals | （整份文件完全沒提） | 「本次不含：企業發票開立、多角色後台權限（本次只有單一管理員角色）、會員點數系統」 |

**判斷標準**：如果把範例句子拿給另一個工程師，他能不能不問你、直接動手寫出對應的程式碼或測試案例。「做好錯誤處理就好」沒有人能直接動手；「email 重複回 409 並顯示指定文字」可以。

## 5. 實戰案例一：電商系統

客戶原話：「我要一個電商網站，可以賣東西、收款、出貨。」

**第一層：功能邊界**
- 要做：商品列表／商品詳情頁、購物車、單一金流（信用卡，串第三方金流 Checkout）、訂單狀態（待付款／已付款／已出貨／已完成）、Email 通知訂單狀態變化。
- Non-Goals：多倉庫庫存管理、跨境金流／多幣別、優惠券與促銷規則引擎、會員等級折扣、超商取貨整合（本次只支援宅配）。

**第二層：資料模型欄位（節錄）**
```text
product(id, name, price_cents, stock_qty, is_active)
order(id, member_id, status ENUM('pending','paid','shipped','completed','cancelled'),
      total_cents, created_at)
order_item(order_id, product_id, qty, unit_price_cents)
```

**第三層：邊界異常處理**
- 下單時商品庫存不足 → 擋下該筆訂單，回傳「庫存不足，剩餘 N 件」，不做部分出貨。
- 金流 Callback 逾時或失敗 → 訂單維持 `pending`，不得提前標記 `paid`；需有背景排程重新查詢金流狀態。
- 訂單已 `shipped` 後客戶要求取消 → 系統不允許直接取消，需走人工客服流程（本次原型只需顯示「請聯繫客服」提示，不做自動退款邏輯）。

## 6. 實戰案例二：會員系統

客戶原話：「做一個會員系統，之後要分付費等級。」

**第一層：功能邊界**
- 要做：Email+密碼註冊/登入、忘記密碼、會員等級（`free`／`paid` 兩級，欄位先建好）、管理員可在後台手動調整單一會員的等級。
- Non-Goals：金流訂閱自動扣款與升降級（本次等級變更只能靠管理員手動，不含自動續訂）、第三方 OAuth 登入、多角色後台權限（本次後台只有一種管理員角色）。

**第二層：資料模型欄位（節錄）**
```text
member(id, email UNIQUE, password_hash, level ENUM('free','paid') DEFAULT 'free',
       level_changed_at, created_at)
admin_action_log(id, admin_id, member_id, action, created_at)
```

**第三層：邊界異常處理**
- 註冊時 email 已存在 → 回傳 409，提示改用忘記密碼。
- 重設密碼連結用過一次後 → 立即失效，不可重複使用；過期時間 24 小時。
- 管理員調整會員等級 → 寫入 `admin_action_log`，前端顯示「此操作會被記錄」，防止日後「是誰改的」扯皮。
- 會員帳號被停用（本次原型假設有一個 `is_active` 布林欄位）後嘗試登入 → 回傳明確訊息「帳號已停用」，不可與「密碼錯誤」用同一句話混淆（避免使用者誤判為忘記密碼而重複嘗試）。

## 7. 與其他範本的關係

- 解壓縮完成、簽約前，請接著使用 [`docs/freelance-contract-scope-and-prerequisites-spec.md`](../docs/freelance-contract-scope-and-prerequisites-spec.md) 將本範本第 1 層的 Non-Goals 寫入合約的 Scope 條款與前提時程；本範本負責「拆出邊界」，該文件負責「把邊界寫成有拘束力的條款」。
- 本範本第 3 節的 HTML 原型結構，可與 `docs/web-to-app-freelance-workflow.md`、`templates/single-file-creative-coding-skill.md` 的既有 Single-file 產出規範合併使用，不另訂一套互動 HTML 規則。
