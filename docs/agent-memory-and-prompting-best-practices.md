## 1. Agent 記憶治理：存策略與已驗證規則，不存易過時狀態

### 1.1 Anthropic 官方數據與適用邊界

1. **CL-Bench 跨工作階段記憶效益（限 Managed Agents 評測）**：
   - 依 Anthropic〈The components of agent memory〉（2026-11-06），`Claude Opus 5.5` 在 **CL-Bench 資料庫代理評測**中，啟用跨工作階段記憶（Cross-session Memory）後，平均得分由 `0.655` 提升至 `0.838`（**相對提升約 28%**）。
   - **適用邊界**：此 28% 提升係針對 **Claude Managed Agents 之 CL-Bench 基準測試**，不可直接外推宣稱「一般聊天視窗日常問答皆提升 28%」。

### 1.2 《寶可夢 紅》三代模型記憶紀錄（案例觀察，非檔案數之因果證明）

Anthropic 在〈The components of agent memory〉中揭露了三個不同模型遊玩《寶可夢 紅》的記憶檔案紀錄：

| 模型版本 | 記憶檔案規模與結構 | 遊戲進度表現 | 官方指出的行為特徵 |
| :--- | :--- | :--- | :--- |
| **Claude Sonnet 3.7** | 建立 **413 個記憶檔**，分散於 **225 個資料夾** | 僅獲得 **1 枚徽章** | 記下大量**可直接從當前畫面讀到、且很快過時的瞬時狀態**；維護與翻找龐大記憶樹反而耗盡上下文與推理資源 |
| **Claude Fable 5** | 約 **10 個檔案**（9 個檔案分置於 2 個資料夾，另加 1 個 `global.md`） | 獲得 **4 枚徽章**（未通關） | 捨棄瞬時畫面狀態，保留**自己推導出來並驗證過的策略與規則** |
| **Claude Opus 5.5** | 官方僅描述「記憶資料夾很小」（**未公布具體檔案數**） | **成功通關** | 具備更強的基礎推理能力與精簡筆記習慣 |

> **方法論警示（嚴禁寫成因果規律）**：
> 上表是**三個不同能力世代的模型各跑一次的案例觀察（Case Observation）**，實驗並未固定同一模型來單獨控制「記憶檔案數量」變數。因此，**不能宣稱「記憶檔案越少就必然表現越好」或將檔案數量當作通關的因果證明**。
>
> **可採用的工程實踐**：
> 記憶治理的重點不在於硬性限制檔案個數，而在於**「區分瞬時狀態（Ephemeral State）與持久策略（Verified Strategy）」**——凡是能從當前程式碼、終端機狀態或畫面直接查到的易過時資訊，一律不寫入長期記憶；長期記憶（如 `agent-assets`、`AGENTS.md`、專案 `REVIEW.md`）只保存**經過驗證的架構決策、防呆規則與跨 Session 教訓**。

### 1.3 專案隔離與記憶定期收斂

- **多專案記憶隔離（Projects Memory Isolation）**：在管理多個不同客戶或獨立儲存庫時，應在 Project 的 Memory 設定中關閉 `Use account memory`（或保持專案級規則獨立），防止全域個人偏好污染特定專案的嚴格規格。
- **記憶定期重構（【二手轉述，待測】）**：Ruben Hassid 建議定期以「保留、修正、刪除」三分法清理長期記憶（文中舉例將 105 條記憶收斂至 26 條）；此數字與做法屬作者個人經驗之二手轉述，在本機環境列為待測參考，實務上以本機 `neat-freak` 事實對帳流程為準。

## 2. 對話除錯與跨 Session 接手規範（附適用條件之可選策略）

當 AI 在多輪對話中出現方向偏離或錯誤回答時，應依錯誤性質選擇「直接糾正」或「編輯原提問建立新分支」，而非盲目套用單一做法：

```text
[模型回答出現錯誤或偏離]
   │
   ├─► 情境 A：單一事實錯誤 / 局部小瑕疵 (前提與方向正確)
   │     └── 策略：直接在下一輪對話指出錯誤並提供正確事實 (Iterative Refinement)
   │     └── 依據：Anthropic 官方文件與原文皆肯定以接續提示要求模型查核並修正局部錯誤
   │
   ├─► 情境 B：反覆受錯誤前提影響 / 需求一開始沒講清楚導致整條推理走偏
   │     └── 策略（可選）：回到出錯前的「使用者原提問」點選 Edit 修改並重送（建立新對話分支），或整理已確認資訊另開新對話
   │     └── 理由：錯誤的假設與長篇無效爭辯會留在當前分支脈絡中持續干擾注意力；切出新分支比在末端疊加補丁更乾淨
   │
   └─► 情境 C：長任務跨日接續 / 上下文逼近壓縮臨界點
         └── 策略：先產出結構化交接摘要（或 HANDOFF.md），再開啟新 Session 接手
```

### 2.1 三種對話修正與接手策略對照表

| 策略名稱 | 性質與證據等級 | 適用條件（When to Use） | 不適用情境與注意事項 |
| :--- | :--- | :--- | :--- |
| **1. 後續提示直接糾正（Iterative Refinement）** | **官方標準做法**（Anthropic 官方提示工程文件建議） | 單一事實錯誤、漏看某個邊界條件、格式微調，且整體任務前提未被污染 | 若已連續糾正 2～3 輪仍在同一死胡同打轉，應停止繼續追問，改用策略 2 |
| **2. 編輯原提問建立新分支（Edit Original Prompt）** | **可選策略**（須視前提是否受污染而定） | 初始提示詞有歧義、模型從第一步就誤解架構方向，且後續脈絡已被大量錯誤推理佔據 | 注意在 Claude Web / Desktop 點選 `Edit` 是**從該節點建立新的對話分支（Branch）**，並非「重置系統底層」；單純小錯無需動用 |
| **3. 跨 Session 10 行交接摘要（10-Line Handoff Summary）** | **【二手轉述，待測】**（出自 Hassid 個人經驗轉述） | 長對話準備切換新視窗時，要求先輸出「目標、已確認決定、重要背景、未完成事項」摘要 | 「10 行」為經驗法則而非硬指標；在多 Agent 工程環境中，應優先使用標準化的 `agent-handoff` / `checkpoint` 技能寫入實體檔案 |

## 3. 高槓桿提示詞結構與防幻覺／隱私安全紅線

### 3.1 提示詞工程核實邊界

1. **「目標＋背景＋允許反問」結構**：
   - 在提示詞中明確授權模型「若缺少關鍵資訊，請在動手前先向我提問」，能有效減少模型在需求不明時的盲目猜測（完全呼應本機全域規範「不確定使用者意圖時先詢問，不自行假設」）。
   - **防幻覺邊界校正**：允許反問**不能保證消除事實幻覺**。依 Anthropic 官方減少幻覺的指引，針對事實查核與文獻分析，必須同時結合：(1) 明確允許模型回答「我不知道／資料未提及」；(2) 要求先逐字引述原文（Quote First）再下結論；(3) 對關鍵引用與外部數據進行獨立查證。
2. **反向批判提問（Red-Teaming Prompt）**：
   - 評估技術方案或商業決策時，避免使用「你覺得這個想法是不是很棒？」等引導式提問（易觸發模型討好傾向 Sycophancy），應強制要求：「列出這個方案最可能失敗的 3 個技術／營運風險與反對理由」。

### 3.2 回饋資料保留與隱私安全防線（附官方依據）

- **讚／倒讚（Thumbs Up / Down）之 5 年資料保留風險**：
  - 依 [Anthropic 隱私中心官方說明](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training)（該頁主要說明商業方案規範，個人方案另有對應條款），當使用者在對話中主動點擊回饋按鈕（讚或倒讚）並提交意見時，**相關的完整對話內容可能會被保留最長達 5 年**，並**可能**被用於安全研究與模型訓練（並非每一筆必然用於訓練，且在使用前會與使用者帳號 ID 脫鉤）。
- **本機操作硬閘門**：
  1. 凡涉及內部程式碼、客戶資料或敏感架構的對話，**提交任何回饋前必須先確認當前帳號方案之隱私條款，原則上禁止在涉密對話點選讚／倒讚回饋**。
  2. 上傳任何財務、銀行 CSV 或業務表格請 AI 製作儀表板或分析前，必須先在本地完成**個資去識別化（De-identification）**，並嚴格遵守「API key、token、私鑰不進對話」之全域鐵律。
