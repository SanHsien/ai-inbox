## 2. 為什麼不能只照做「5 個 Agent」

五個 Agent 跑**同一個任務**，只能回答「這件事在這個任務上有沒有明顯差距」，不能回答「這份知識整體有沒有用」。原因有二：

1. 一個任務代表不了這份知識的適用範圍；
2. 樣本小，只有極大的差距才看得出來。

以對照組、實驗組各 5 次、成功與否為二元結果計算（Fisher 精確檢定，單尾，2026-11-02 以 Python 標準函式庫實際算出）：

| 實驗組成功 | 對照組成功 | p 值 |
| :-: | :-: | :-: |
| 5/5 | 0/5 | 0.004 |
| 4/5 | 0/5 | 0.024 |
| 5/5 | 1/5 | 0.024 |
| 4/5 | 1/5 | 0.103（不顯著） |

所以 5 對 5 只能抓「幾乎全有 vs 幾乎全無」；4/5 對 1/5 這種看起來差很多的結果，也還不能下結論。因此本協議分兩階段：

- **階段 1（快篩）**：照作者做法，5 對 5、單一任務，用來決定這份知識「值不值得花力氣做階段 2」，**不能用來做刪除決定**。
- **階段 2（正式）**：多個任務、每任務重複多次，才能做保留或刪除的決定。

## 3. 實驗流程圖

```text
   選定受測知識 K（一個 AGENTS.md 段落 / 一個 Skill / 一份 doc）
                         │
                         ▼
   ① 寫假設：K 預期改善哪一類行為？（例如「不吞例外」「先查證再寫」）
                         │
                         ▼
   ② 出題：N 個任務，會觸發 K；另加 2 個誘餌任務（與 K 無關）
      每題先寫好「外部裁判」（測試／驗證器），並固定不改
                         │
                         ▼
   ③ 預先登記（pre-register）：成功定義、指標、判定閾值，寫進實驗紀錄後不得改
                         │
                         ▼
   ④ 建立兩種環境（同一 commit）：
        控制組 C：全新歷史、不含 K       實驗組 T：全新歷史、含 K
                         │
                         ▼
   ⑤ 隨機化：每題每組各跑 r 次，執行順序隨機，環境用中性代號
                         │
                         ▼
   ⑥ 執行（同模型版本、同提示詞、無人介入）
                         │
                         ▼
   ⑦ 收資料：裁判 exit code、token、回合數、純淨度（腳本計算，不問 Agent）
                         │
                         ▼
   ⑧ 檢查有效性（第 7 節）──不合格──▶ 判無效，修正設計後重做
                         │合格
                         ▼
   ⑨ 解盲、統計（第 6 節）──▶ 保留 / 降級 / 移除 / 無結論
```

## 4. 實驗設計：樣本怎麼定

| 參數 | 值 | 理由 |
| :--- | :--- | :--- |
| 任務數 N | 10（正式）；階段 1 為 1 | 任務層級的配對比較（第 6 節）至少要有 8 個「有勝負」的任務才有可能達到顯著；10 題留出平手的空間 |
| 每題每組重複 r | 3 | 模型輸出有隨機性，單次結果不能代表該題；3 次是成本與雜訊之間的折衷 |
| 總執行次數 | N × 2 × r = 60 | 先估 token 成本再開跑 |
| 誘餌任務 | 另加 2 題與 K 無關的任務 | 檢查 K 有沒有「拖累」不相關任務（注意力稀釋），不列入勝負統計，單獨報告 |

任務的選擇：

- 從專案真實的歷史任務或 issue 抽，不要為了讓 K 看起來有用而設計。
- 能被機械式外部裁判判定（測試、`verify_*.py`、型別檢查）。裁判做法參考 [`external-judge-audit.md`](./external-judge-audit.md)；**不用 LLM 當主要裁判**。
- 難度要有鑑別力：先讓控制組跑一次試跑，若全題 100% 成功（天花板）或 0% 成功（地板），換題。
- 任務間不能共用答案（一題的解法不能洩漏給另一題）。

「盲」的定義（作者說 blind，但沒有說誰盲）。本協議的三層：

1. **Agent 不知道自己在實驗**：提示詞只給任務，不提 A/B、對照組、評估。
2. **環境用中性代號**：資料夾叫 `run-<隨機碼>`，不叫 `control`、`with-skill`；組別對應表另存，執行與統計前不讀。
3. **評分者不知道組別**：主要指標由腳本判定（不需要人）；若有人工看產出（純淨度的抽查），只看去除組別資訊的 diff。

Agent 本身無法對「自己手上有沒有這份知識」盲：它看得到自己的檔案。所以這裡的盲指的是「不知道這是實驗、不知道要比較什麼」。

## 5. 評估指標與公式

設任務 `t` 在組別 `g ∈ {C, T}` 的 `r` 次執行中，通過外部裁判的次數為 `k(t,g)`。

| 指標 | 公式 | 說明 |
| :--- | :--- | :--- |
| 任務成功率 | `S(g) = Σ_t k(t,g) / (N·r)` | 「成功」= 外部裁判 exit code 0，且沒有違反範圍限制（動到任務範圍外的檔案算失敗） |
| 每題成功率 | `s(t,g) = k(t,g) / r` | 第 6 節勝負判定用 |
| 一次通過率 | `F(g) = 第一次宣告完成就通過裁判的執行數 / (N·r)` | 「宣告完成」= Agent 結束或明講完成的第一個時點，在該時點用裁判檢查 |
| Token 消耗比 | `R_tok = median_T(tok) / median_C(tok)` | 只算成功的執行；另報「含失敗」的總量。token 以服務商回報的用量為準，不用 Agent 自述 |
| 修正回合數 | `ΔTurns = median_T(turns) − median_C(turns)` | 回合 = 一次 Agent 回覆加其工具呼叫；只算成功的執行 |
| 代碼純淨度 | `P(g) = (範圍外改動檔案數 + linter／驗證器警告數) / max(1, 改動行數/100)` | 每百行改動的問題數，越低越好。不含主觀的「寫得漂不漂亮」 |
| 成功率差 | `ΔS = S(T) − S(C)` | 以百分點表示 |

指標分級（預先登記，不得事後換）：

- **主要指標**：任務成功率 `S`（及其配對檢定）。
- **次要指標**：`F`、`R_tok`、`ΔTurns`、`P`；只用來區分「保留」與「降級」，不單獨導致保留。

## 6. 判定規則

**配對勝負**：對每題 `t`，若 `s(t,T) > s(t,C)` 記實驗組勝（W），`<` 記敗（L），相等記平手（丟掉）。令 `n = W + L`。

**統計檢定**：對 W 做單尾精確二項檢定（假設兩組沒有差別，則 W ~ Binomial(n, 0.5)）。要達到單尾 p < 0.05 所需的最少 W（2026-11-02 以 Python 標準函式庫算出）：

| n（有勝負的題數） | 需要的 W | 對應 p |
| :-: | :-: | :-: |
| 5 | 5 | 0.031 |
| 6 | 6 | 0.016 |
| 7 | 7 | 0.008 |
| 8 | 7 | 0.035 |
| 9 | 8 | 0.020 |
| 10 | 9 | 0.011 |
| 11 | 9 | 0.033 |
| 12 | 10 | 0.019 |

**決策表**（閾值是本 repo 的選擇，不是原文）：

| 條件 | 結論 |
| :--- | :--- |
| 實驗組勝的檢定 p < 0.05，**且** `ΔS ≥ +15` 百分點，**且** `R_tok ≤ 1.3` | **保留** |
| p < 0.05 且 `ΔS ≥ +15`，但 `R_tok > 1.3` | **降級**：縮短內容，或改成按需載入（成本模型見 [`agent-skills-curation-and-context-budget-spec.md`](./agent-skills-curation-and-context-budget-spec.md)），再測一次 |
| 對照組勝的檢定 p < 0.05（把上面 W 換成 L） | **移除**：這份知識有害 |
| `ΔS < +5` 百分點，且 `ΔTurns`、`P` 也沒有明顯較好 | **移除候選**：知識沒有用，且耗成本 |
| 其他（介於之間，或 n < 8） | **無結論**：換一批任務重做，最多重做 2 輪；仍無結論就降級（縮短），不維持原樣 |

「移除」是建議，實際刪除檔案仍需維護者授權；先搬到 `archive/` 或標為停用，比直接刪好。

**不適用本表的知識**：安全護欄與破壞性操作規則（例如「刪除前先確認」）。這類規則的價值是避免罕見的重大錯誤，成功率差看不出來。評估它們要改用對抗式任務（刻意誘導違規），指標改為「違規率」，且不能以「沒有統計差異」為由移除。

## 7. 何時判這次實驗無效

任一條成立，這次結果**作廢**，不能用來做決定，要修正後重做：

| # | 無效條件 | 怎麼偵測 |
| :-: | :--- | :--- |
| 1 | 洩漏組別：Agent 的紀錄中出現 `control`、`treatment`、實驗相關字樣 | 對所有紀錄做字串掃描 |
| 2 | 對照組仍取得 K：控制組環境保有 K 的內容（舊 commit 歷史、其他路徑的副本、全域設定檔、Agent 的記憶機制） | 在執行前，對控制組環境搜尋 K 的特徵字串；執行後檢查工具呼叫紀錄有沒有讀到 |
| 3 | 兩組不只差 K：模型版本、提示詞、工具集合、溫度設定、起始 commit 有差異 | 把設定存檔並逐項比對 |
| 4 | 天花板或地板：控制組成功率 ≥ 95% 或 ≤ 5% | 計算 `S(C)` |
| 5 | 有勝負的題數 `n < 8` | 計算 n |
| 6 | 基礎設施失敗的執行（逾時、API 錯誤、環境壞掉）超過總執行的 20%，或兩組失敗率差 10 個百分點以上 | 失敗原因分類統計；失敗的執行不能直接當「Agent 失敗」 |
| 7 | 裁判本身有問題：把裁判的實作弄壞時它仍通過，或對正確解答判失敗 | 實驗前拿一份已知正確的解、一份已知錯誤的解各跑一次裁判（參考 [`irrefutable-evidence-and-invalid-patterns-spec.md`](./irrefutable-evidence-and-invalid-patterns-spec.md) 支柱 B） |
| 8 | 實驗途中改了閾值、換了任務、換了裁判 | 與預先登記的紀錄比對 |
| 9 | 實驗途中模型被服務商更新（版本字串改變） | 每次執行記錄模型識別字串，全部相同才有效 |
| 10 | 誘餌任務顯示 T 組明顯比 C 組差（成功率差超過 20 個百分點） | 這不是無效，而是「K 拖累不相關任務」的證據；單獨記為發現，並在結論註記 |

## 8. 指令範本

以下是**範本**，需要依你的 Agent CLI 調整。`AGENT_CMD` 要換成你的 Agent 的非互動執行指令，其參數與用量輸出方式本文**未驗證**（各家不同，請查該工具的官方文件）。

**建立環境（全新歷史，避免 Agent 用 `git log` 看到 K）**

```bash
#!/usr/bin/env bash
# 用法：make_arm.sh <repo> <commit> <輸出目錄> <ablate|keep> <K 的路徑...>
set -euo pipefail
repo=$1; commit=$2; out=$3; mode=$4; shift 4
mkdir -p "$out"
git -C "$repo" archive "$commit" | tar -x -C "$out"
if [ "$mode" = "ablate" ]; then
  for k in "$@"; do rm -rf "${out:?}/$k"; done
fi
git -C "$out" init -q
git -C "$out" add -A
git -C "$out" -c user.name=exp -c user.email=exp@example.invalid commit -q -m base
```

**排程：隨機順序與中性代號**

```bash
#!/usr/bin/env bash
# 用法：run_experiment.sh <repo> <commit> <任務目錄> <K 路徑>
# 任務目錄內每題一個資料夾：prompt.txt（給 Agent 的提示）、judge.sh（外部裁判，exit 0 = 通過）
set -euo pipefail
repo=$1; commit=$2; tasks=$3; k=$4
r=3
mapfile -t jobs < <(
  for t in "$tasks"/*/; do
    for arm in C T; do for i in $(seq 1 "$r"); do echo "$(basename "$t") $arm $i"; done; done
  done | shuf
)
: > mapping.private.csv      # 組別對應表：執行與統計前不要打開
for job in "${jobs[@]}"; do
  read -r task arm i <<<"$job"
  id="run-$(head -c6 /dev/urandom | od -An -tx1 | tr -d ' \n')"
  mode=keep; [ "$arm" = C ] && mode=ablate
  bash make_arm.sh "$repo" "$commit" "work/$id" "$mode" "$k"
  echo "$id,$task,$arm,$i" >> mapping.private.csv
  # AGENT_CMD 要換成你的 Agent 非互動指令；提示詞只能來自 prompt.txt，不要加任何組別資訊
  ( cd "work/$id" && AGENT_CMD < "../../$tasks/$task/prompt.txt" > "../../logs/$id.log" 2>&1 ) || echo "agent_rc=$?" >> "logs/$id.meta"
  # 裁判獨立於 Agent，在其結束後才跑
  jrc=0
  ( cd "work/$id" && bash "../../$tasks/$task/judge.sh" ) > "logs/$id.judge" 2>&1 || jrc=$?
  echo "judge_rc=$jrc" >> "logs/$id.meta"
done
```

> 這支腳本是範本骨架：`AGENT_CMD`、token 與回合數的擷取、`logs/` 目錄建立都要依你的環境補。這份文件沒有附可直接執行的 Agent 指令，因為不同 Agent 的非互動參數我沒有查證。腳本以 `bash -n` 檢查過語法。

**解盲與統計**：收齊 `logs/*.meta`（裁判 exit code）後，才讀 `mapping.private.csv`，依第 6 節計算 W、L、n 與 p。

**階段 1（快篩）**：只取 1 題、`r = 5`，同上，但不做決策，只決定要不要進階段 2。

## 10. 已知限制

- 本協議沒有實際跑過，所有閾值（15 個百分點、1.3 倍、20% 失敗率等）都是設計時的估計，沒有經驗數據。第一次實際跑完後，應回頭檢討並修訂。
- 配對檢定假設各題獨立；若多題共用同一段程式碼，勝負會相關，p 值會偏樂觀。
- 該實驗測的是「這份知識在這批任務上、這個模型版本下」的價值；模型更新後結論可能改變，建議每次換主要模型後對保留下來的知識做抽樣複測。
- 60 次執行有 token 成本；知識很多時，先用階段 1 篩，再對值得的做階段 2。
- 作者原文只提到五個盲 Agent，沒有說明對照方式與統計；本文的多任務設計是延伸，不代表作者的做法。
