## 5. Plus 帳號避開 5 小時限制【作者宣稱＋官方佐證】

- 官方確認 Plus 有 5 小時視窗，且 Luna 的估計訊息數遠高於 Sol／Astra（第 3 節）【官方】。
- 作者宣稱做法：用 Luna 6 Max~High，搭配有驗收閘門、有停止條件的 `/goal`，讓 Agent 以穩定速率連續運行；實測 24 小時不撞 5 小時上限、約 2 天用滿週額度【作者實測，單次】。
- 本機 `codex features list` 顯示 `goals` 為 `stable`、預設啟用（2026-10-26，`codex-cli 0.150.0`）。`/goal` 與 5 小時限制的互動**官方文件未查到說明**，第三方文章也只講每個 goal 的 token 預算，不講方案限制。
- 可操作的檢查：開跑前看用量儀表板；為 goal 設明確完成條件與 token 預算；每個 5 小時視窗結束前確認是否接近上限，而不是假設「Luna 不會撞牆」。

## 6. Prompt Caching 四層前綴排版【官方原則＋作者分層】

官方原則【官方】：

- 命中要求**整段前綴完全相同**；前面的內容變了，後面就不能重用。
- 穩定的指令與參考資料放開頭，時間戳、使用者專屬內容放最後；GPT-5.6 以後建議在靜態內容後加明確的快取斷點（breakpoint）。
- 最低可快取長度：GPT-5.6 及之後為 1,024 個可見輸入 token。
- 價格：快取讀取為未快取輸入的 0.1 倍（GPT-6.1 Sol 為 0.05 倍）；快取寫入 1.25 倍（預設 30 分鐘）或 2.5 倍（12 小時，Responses API）。

作者分層（把官方原則套到多專案派工）：

```text
┌──────────────────────────────────────────────────────────────┐
│ Layer 1 全靜態   系統提示、全域規則(AGENTS.md)、不可變環境事實      │ ← 命中率最高
├──────────────────────────────────────────────────────────────┤
│ Layer 2 專案靜態 架構索引、DB Schema、核心介面契約                │
├──────────────────────────────────────────────────────────────┤
│ Layer 3 半動態   近期相關程式碼快照                              │
├──────────────────────────────────────────────────────────────┤
│ Layer 4 全動態   本輪請求、暫存變數、最新測試錯誤輸出              │ ← 不快取
└──────────────────────────────────────────────────────────────┘
   靜態在前、動態在後；Layer 1~2 在斷點之前
```

作者宣稱：靜態前綴命中率可達 75%~90% 以上、可降低 80% 以上重複 token 成本【作者實測，無方法細節，未驗證】。注意官方價格下 Sol 的快取輸入是未快取的 5%，所以「降本幅度」取決於你的前綴占比，不要直接套 80%。
