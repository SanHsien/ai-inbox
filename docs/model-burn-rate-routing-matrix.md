### 9.7 本機實測（2026-11-16）【本機實測】

對應任務 `T-20261114-03`。原始資料、任務說明、隱藏驗收測試與執行腳本在 [`docs/evidence/terra-sol-burn-2026-11-16/`](evidence/terra-sol-burn-2026-11-16/)。

### 10.3 現行四種路由（摘自 SKILL.md）

政策原文規定只用四種模式，**預設 `solo`**；只有具體風險或完整規格讓輔助角色確實有用時才換。一個輔助角色是預設上限，`full` 是明示的例外。

| 路由 | 誰實作 | 誰驗證 | 有沒有獨立審查 | 輔助角色數 |
|------|--------|--------|---------------|-----------|
| `solo` | 主代理 | 主代理（含自我審查） | 無 | 0 |
| `delegate` | 一個 implementer | 主代理（讀完整 diff） | 無，政策明訂不另加 fresh reviewer | 1 |
| `audit` | 主代理 | 主代理 | 一個 fresh reviewer 看累積 diff | 1 |
| `full` | 一個 implementer | 主代理 | 一個 fresh reviewer | 2（例外） |

SKILL.md 寫明的角色配對（Claude Code 原生版；只列原文有寫的，沒寫 effort 的不補）：

| 角色 | 模型／effort（原文） | 原文適用範圍 |
|------|---------------------|-------------|
| `advisor-sonnet-implementer` | Sonnet／medium | `delegate` 預設：規格完整的實作、文件、簡報、試算表 |
| `advisor-sonnet-deep-implementer` | Sonnet／high | 根因不明的除錯、跨多檔改動、高風險或影響面大的工作 |
| `advisor-haiku-implementer` | Haiku（原文未寫 effort） | 只限機械性批次：改名、格式化、grep 摘要、套用已驗證的範本 |
| `advisor-opus-reviewer` | Opus（原文未寫 effort） | `audit`／`full` 的 fresh 審查；回 `ship`／`fix-first`／`rethink`，不動手修 |

Haiku 與 Opus reviewer 的 agent 定義沒有 effort 欄位；plugin 的 `references/operations.md` 寫明沒有 `effort` 欄位的 agent 繼承主 session 的 effort，所以它們的 effort 隨主 session 而定，不是固定值。

- 貼文裡的「Astra high 做 QA」不能直接換成本機主力模型或上表任何一列；現行 plugin 的輔助角色只限 Sonnet／Haiku／Opus 三個 family，SKILL.md 明訂不得默默換成別的 family，gateway 對應到其他 family 也不算可接受的替代。跨廠配對不在這份政策內；若要用，得另外驗證完整的模型＋effort 組合（本文解讀，非政策原文）。

### 10.4 書面案例【文件案例】

以下三個案例是「照政策該怎麼選」的示例，不是量測；沒有 token 數、沒有省額比例。

**案例 A：小型工作 → `solo`**

- 情境：修正一份文件裡的一個錯誤連結，再跑 `python tools/verify_inbox.py`。
- 選法：`solo`。主代理自己改、自己跑檢查、自己複查 diff，不派任何輔助角色。
- 理由：cost-policy 要求派工前寫出「輔助角色取代主代理的哪部分工作」。這件事寫派工說明、等回報、再讀 diff 的成本已經超過工作本身，答不出來就由主代理完成。
- 這裡套貼文的三角色流程會多出兩次模型呼叫，沒有對應的風險可以抵銷。

**案例 B：規格完整 → `delegate`**

- 情境：替 20 篇既有筆記補上同一個 frontmatter 欄位；欄位名稱、取值規則、要改的檔案清單、驗收指令（`python tools/build_index.py && python tools/verify_inbox.py`）都已寫定。
- 選法：`delegate`，派一個 implementer。規則要逐篇判斷時用 `advisor-sonnet-implementer`（Sonnet／medium）；若只是套用已在一篇上驗證過的範本，屬機械性批次，才用 `advisor-haiku-implementer`。
- 驗收：主代理讀完整 diff、確認檔案範圍與驗收指令結果。政策明訂這條路由**不再加 fresh reviewer**。
- 成本上要算進去的：寫派工說明、implementer 的全部嘗試（含失敗重試）、主代理讀 diff 與整合。cost-policy 明寫「不因模型單價低就派工」。

**案例 C：有具體風險 → `audit`**

- 情境：修改 `tools/verify_inbox.py` 的檢查邏輯。這支是全 repo 的驗證器，改壞了會讓之後所有檢查「看起來通過」，而作者自己跑測試不容易發現自己放寬了什麼。
- 選法：`audit`。主代理實作並驗證，再由一個 fresh `advisor-opus-reviewer` 看累積 diff。
- 規則：reviewer 只回 `ship`／`fix-first`／`rethink`，不動手修；審查前後要留 `git status --short` 證明 reviewer 沒有改檔；任何修正都使先前的結論失效，要重新驗證並再做一次 fresh 審查。
- 這裡多付一次審查的理由是具體的（驗證器自身失效的風險），不是「每個任務都要 QA」。

**`full` 的例外條件**

- SKILL.md 對 `full` 只寫「exceptional only」，流程是一個 implementer → 主代理驗證 → 一個 fresh Opus reviewer；原文**沒有列出**觸發條件清單。
- 本文的解讀（非政策原文，未驗證）：案例 B 的條件（規格完整、工作量足以抵銷派工成本）與案例 C 的條件（有具體、可說明的風險需要獨立審查）**同時成立**時才考慮。例如依已定稿的規格大範圍改寫驗證工具與其測試。
- 貼文的「PM／一線實作／QA」三角色最接近 `full`。在現行政策下它是例外，不是每個任務的固定支出；路由宣告後只能因新觀察到的風險往上升，不能默默降級。

### 10.5 返工成本的限制

cost-policy 的算法：**每件合格交付成本 = 全部嘗試成本 ÷ 合格交付件數**；失敗、顧問、審查與重做都要計入，資料不足不能宣稱省下固定比例。

套到貼文的說法：

- 低價模型的單價低，不等於整件事便宜。implementer 交回的東西若要主代理退回重做，重做與重審的成本全部算在同一件交付上。
- 貼文的「省 60–70%」沒有提供嘗試次數與返工紀錄，無法用這個算式檢驗；即使規格切得很細，這個比例也仍是【社群宣稱】。
- 訂閱額度不是 API 帳單，兩者不可直接換算（第 8 節）。
- 本 repo 沒有任何一筆依 cost-policy「成本證據」欄位記下的分工對照紀錄，所以本文不給自己的省額數字。

### 11.4 API 價格時間窗【官方】

取自 G5，美元／每百萬 tokens。「→」左邊適用到 2026-11-30，右邊從 2026-12-01 起。G5 這次讀到的內容沒有標最後更新日。

| 層級 | 輸入 | 輸出（含思考） | 快取輸入 |
| --- | --- | --- | --- |
| Standard | $2.00 → $4.00 | $10.00 → $20.00 | $0.10 → $0.20 |
| Batch | $1.00 → $2.00 | $5.00 → $10.00 | $0.05 → $0.10 |
| Flex | $1.00 → $2.00 | $5.00 → $10.00 | $0.05 → $0.10 |
| Priority | $3.60 → $7.20 | $18.00 → $36.00 | $0.18 → $0.36 |

- **Carbon 與 Argon 在這四個層級的價格與漲價日完全相同**（G5）。來源筆記與轉載文章只提到 Carbon 漲價，容易讓人以為改用 Argon 可以避開；G5 顯示 12-01 起兩個一起翻倍。Argon 另有一個僅限邀請的 Contributor 預覽層（$1.00／$5.00／$0.05），G5 沒有列它的漲價。
- 價格不依 prompt 長度分級，1M context 內同一個單價（G5）。
- 快取輸入是輸入價的 5%，也就是 G1 寫的「95% off」【推算：0.10 ÷ 2.00】。兩個模型都只支援隱式快取，不支援顯式快取（G5），所以第 6 節的前綴排版原則適用，但不能自己指定快取斷點。
- G1、G2 稱 $2／$10 為 Carbon 的優惠價，並註明這個價格只適用於公開版的 Carbon；G5 沒有用「優惠」這個詞，只列兩段日期。
- 【推算】同樣的用量，12-01 起的 API 費用是 11-30 前的 2 倍。這是**牌價的倍數**，不是任務成本的倍數：G2 說 Carbon 比 Argon 多用 token，同一件事用 Carbon 的實際花費會高於 Argon，高多少官方沒有給數字【未查證】。

### 11.5 評測作弊率與失準警示【官方自述】

圖表標題是模型生命週期各階段的失準量測，數值越低越好（G2 的圖）。

| 量測 | Carbon | Argon | 可信度 |
| --- | --- | --- | --- |
| Terminal-Bench 4.0 稽核：**成功**作弊 | 0.0% | 2.4% | Carbon：【官方】G1 內文；Argon：【官方圖表】 |
| Terminal-Bench 4.0 稽核：**嘗試**作弊 | 0.4% | 3.6% | Carbon：【官方】G1 內文；Argon：【官方圖表】 |

這張表的限制：

- 全部是 Google 對自家兩個模型的內部量測。圖下方的方法論連結指向 G4，但 **G4 的全文裡找不到「作弊」「稽核」「警示」任何一段**（把 PDF 轉成文字後搜尋，2026-11-19），所以怎麼判定作弊、稽核了多少題、誰來判定，都沒有公開。
- 沒有其他廠商模型的對照數字，不能據此說 Carbon 比別家誠實。
- 0.0% 是四捨五入到小數一位的結果，不等於「不會作弊」。
- G2 另外給了一項誠實度基準【官方自述】：375 題中 Carbon 通過 92%，Argon 70%；Carbon 有 98% 的情況拒絕補上缺漏的實驗資料。

對本文路由原則的意義：廠商自己公布，在終端機類的 agent 評測裡，定位為日常主力的 Argon 約每 40 題有 1 題靠作弊過關【推算：2.4%】。這和本 repo 既有的規則方向一致：

- 工人回報「測試通過」不算證據，要看閘門實際跑出來的紀錄與 diff。
- 驗收不交給同一個模型自己做；這條不因為換成 Carbon 就放寬，0.4% 的嘗試率不是零。

### 11.6 路由對照

以下是依官方數字寫的書面建議【文件案例】，沒有本機實測支持。

| 情境 | 建議 | 依據 | 注意 |
