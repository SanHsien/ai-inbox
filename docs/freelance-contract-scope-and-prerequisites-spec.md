## 2. 時程前提條款（Prerequisites Clause）範本

### 2.1 問題：為什麼不能寫死死線

死線（Deadline）綁的是**日期**；但交付時程通常依賴客戶端的動作（提供素材、確認規格、提供金流金鑰）。客戶遲交素材，死線沒跟著動，等於工程師獨自承擔客戶自己的延誤。

### 2.2 條款範本（中文，供起草參考）

```text
第 __ 條　交付前提與時程

1. 甲方（客戶）應於本合約簽署後 __ 個工作日內，提供以下前提資料予乙方（受託人）：
   (1) __________（例：金流服務商 API 金鑰與測試帳號）
   (2) __________（例：第一層功能邊界確認書，簽字版，依附件一）
   (3) __________（例：品牌視覺素材：Logo、主色、字體檔案）

2. 乙方之交付期限為「甲方完整提供第 1 項全部前提資料之日」起算 __ 個工作天，
   而非本合約簽署日起算。

3. 若甲方逾期提供前提資料，乙方交付期限按實際延誤天數同等順延，
   乙方不因此負遲延責任。

4. 若甲方提供之前提資料與附件一（功能邊界確認書）不一致，
   乙方得要求甲方重新確認後，前提資料始視為「完整提供」。
```

### 2.3 前提公式

```text
交付日 = 前提資料完整提供日 + 約定工作天數 + Σ(已核准 CR 增加天數)
```

- 「前提資料完整提供日」要有**書面或可稽核的時間戳**（Email、工單系統、簽名確認書），不能只靠口頭。
- 任何一項前提沒到齊，交付日公式不成立，不得被客戶要求「先照原死線趕」。

## 3. Scope 鋼鐵防線與 Change Request（CR）流程

### 3.1 合約內 Scope 條款範本

```text
第 __ 條　委託範圍

1. 本合約之委託範圍，以附件一「功能邊界確認書」所載之「要做項目」為限，
   並以附件二「資料模型規格書」所載欄位為實作依據。

2. 附件一所列「Non-Goals（本次不做項目）」明確排除於本合約範圍之外，
   非經雙方另行簽署變更單（Change Request，以下稱 CR），乙方無須實作。

3. 甲方於專案執行期間提出之任何需求，若超出附件一「要做項目」範圍，
   或屬附件一所載「Non-Goals」，均視為新需求，應依第 __ 條 CR 流程處理，
   不適用原報價。
```

### 3.2 Change Request 流程

```text
客戶提出新要求
     │
     ▼
比對附件一（Scope）── 在「要做項目」內？ ──是──▶ 原合約範圍，照常實作
     │
     否（屬 Non-Goals 或全新項目）
     ▼
填寫 CR 單：變更內容、預估工時、加價金額、對原交付日的影響
     │
     ▼
雙方簽署 CR 單（書面或工單系統留痕）
     │
     ▼
視為原合約之附加條款，交付日依第 2.3 節公式重新計算
```

CR 單最小欄位：`CR 編號`、`提出日期`、`變更內容描述`、`對照附件一判定（不在 Scope 內的理由）`、`加價金額`、`交付日影響天數`、`雙方簽署`。

## 4. Bug vs 新需求判定表（Definition of Done 分界線）

### 4.1 鐵律

> 規格書有寫但跑不出來 = **Bug**（免費修復）；規格書沒寫但客戶想要 = **新需求**（走 CR 加價）。

這條鐵律能成立的前提是：規格書（附件一、附件二）要寫得具體到「可以直接變成測試案例」——這正是 `templates/client-requirement-decomposition-prompt.md` 第 4 節反例對照要求的標準。規格寫得空泛（例如「做好錯誤處理就好」），這張判定表就會失靈，因為沒有「規格書有寫」這個比對基準。

### 4.2 判定表

| 情境 | 規格書（附件一/二）是否明確記載 | 實際結果是否與規格一致 | 判定 | 處理 |
| :--- | :--- | :--- | :--- | :--- |
| email 重複註冊沒有擋下 | 是（附件一寫明「email 唯一，重複須回 409」） | 否（系統沒擋，可重複註冊） | **Bug** | 免費修復 |
| 客戶要求新增「忘記密碼要改成用手機號碼驗證」 | 否（附件一寫的是 Email 連結，Non-Goals 未排除但也未包含手機驗證） | — | **新需求** | 走 CR |
| 客戶說「訂單狀態邏輯怪怪的」，但沒說清楚哪裡怪 | 需先對照附件一的訂單狀態定義逐一比對 | 需實測才能判定 | 先查證，查無規格依據則視為新需求 | 回報比對結果給客戶再決定 |
| Non-Goals 明確排除的項目（如優惠券引擎）客戶事後要求補上 | Non-Goals 已排除 | — | **新需求** | 走 CR，不得主張「本來就該有」 |

### 4.3 查無規格依據時的標準回覆（可直接套用）

```text
「依附件一第 __ 項，這個情境目前沒有書面規格記載期望行為。
為了避免日後爭議，我們需要先補一份 CR 單定義期望行為（參考反例對照的具體寫法），
確認後再排入工時。若您認為這屬於附件一已有的既定行為，
請指出對應的條款編號，我們會優先核對。」
```

## 5. 報價話術與談判手冊

### 5.1 三種報價法對照

| 報價法 | 計算基礎 | 適用情境 | AI 時代的侵蝕風險 |
| :--- | :--- | :--- | :--- |
| 薪水法（工時 × 時薪） | 預估工時 | 範圍極小、客戶只要「照表操課」的工作 | 高：AI 讓工時縮短，按工時收費只會越做越窮（作者宣稱） |
| 請人成本法 | 客戶若自聘正職工程師的全部成本（年薪 × 約 1.3，涵蓋勞健保、設備、資遣風險，作者宣稱之估算係數，實際比例應按當地人事成本重新估算，**未查證**為普適係數） | 客戶在比較「外包」vs「自聘」時 | 低：錨點是客戶的機會成本，不是你的工時 |
| 價值報價法（Value-Based Pricing） | 系統帶來的增量營收或節省成本之一部分 | 能量化商業價值的專案（如電商轉換率提升） | 低：但需要客戶能接受「分享價值」的談判框架 |

### 5.2 談判話術範本

**開場定錨（請人成本法）**：
```text
「如果您自己聘一位能做這個系統的工程師，年薪大約落在 __ 萬，
加上勞健保、設備與日後離職的交接風險，實際成本通常是年薪的 1.3 倍左右
（此係數為業界粗估，實際請依您所在地區的人事成本抓一個區間，不是固定公式）。
我們這次報價 __ 萬，等於用一次性成本換到不用承擔長期聘僱風險的交付。」
```

**價值報價轉換（有量化依據時）**：
```text
「這個功能上線後，依您提供的歷史數據估算，預計每月可帶來 __ 的增量營收／
節省 __ 的人力成本。我們的報價以此價值的一部分計算，而非單純工時計價。」
```

**客戶殺價到「按工時」邏輯時的回應**：
```text
「如果按工時計價，表示我用 AI 加速完成的部分，省下來的時間成本是我吃掉，
您並沒有少付。價值報價法是把『系統上線後為您創造的效益』當基礎，
這對雙方都更公平。」
```

**遇到「順便加一下」時的標準回應**（對應第 3 節 CR 流程）：
```text
「這個項目不在我們附件一的範圍內，我幫您先寫一張 CR 單，
註明影響的交付天數與費用，確認後我們就排進去，不會耽誤您原本的功能。」
```

### 5.3 什麼時候不適合用價值報價法

- 客戶無法或不願意提供量化數據（營收、轉換率、成本）時，價值報價法沒有可信的計算基礎，應退回請人成本法起步談。
- 專案本質是維護性質（修 Bug、小改版）而非新創造價值時，價值報價法不適用，仍以工時或固定維護費計價。

## 6. 使用提醒

1. 第 2、3 節的條款文字是**起草參考**，不是可直接簽署的完整合約；完整合約需加入準據法、爭議解決、保密條款（NDA）、智慧財產權歸屬等本文件未涵蓋的一般條款，這些請律師補齊。
2. 第 5.2 節「年薪 × 1.3」僅為話術示範中常見的粗估說法（作者宣稱），不同地區社會保險費率、資遣法規差異很大，報價前應自行核算或請會計/人資顧問確認。
3. 與 [`templates/client-requirement-decomposition-prompt.md`](../templates/client-requirement-decomposition-prompt.md) 搭配使用順序：先解壓縮需求產出附件一/二 → 套用本文件第 2、3 節條款 → 簽約 → 執行中用第 4 節判定表處理爭議 → 新需求一律走第 3.2 節 CR 流程。
