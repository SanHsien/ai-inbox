> 對應任務：`T-20261026-25`｜來源筆記：[`notes/2026-10-26-ai-shared-memory-template-team-collaboration.md`](../notes/2026-10-26-ai-shared-memory-template-team-collaboration.md)
> 評估對象：[Private Repo: 跨Agent資產庫]（跨 Agent 共用規則、知識、技能的 SSOT；私有，以下只寫結構與數字，不貼內容）
> 佇列機制出處：[`Leoceeport/ai-memory-template`](https://github.com/Leoceeport/ai-memory-template) @ `ad84653`，規格整理見 [`docs/ai-shared-memory-engineering-spec.md`](./ai-shared-memory-engineering-spec.md) 第 4 節。

## 結論

**現階段不採用「放在 SSOT 倉庫內的 `correction-queue.jsonl`」。** 理由有三，每一條都對得上倉庫自己的規則或可量測的數字：

1. 它和既有規則直接牴觸（第 2 節 C1～C3）；
2. 它要解決的問題（多個寫入者互相覆蓋規則主表）在這個倉庫裡**沒有發生的證據**（第 3 節）；
3. 倉庫已經有一套等效的審核流程，缺的只是「逐條」粒度（第 4 節）。

保留一個**可啟動的替代方案**（佇列放倉庫外、本機私有）與明確的**重新評估觸發條件**（第 5、6 節）。

---

## 1. 要評估的操作流

任務原文：各 Agent 在會話糾正時，先把教訓寫進 `correction-queue.jsonl`，再由主 Session 審核後合入 `lessons.md`。

```text
現況（SSOT 契約 + 操作手冊 第 1 項）
  Agent 發現可重用教訓 ─▶ 由被指派的 Agent/主 Session 改 knowledge 檔（附來源與日期）
        ─▶ 更新雜湊（登記簿狀態回到待審）─▶ 推送閘門（單元測試、倉庫驗證、部署檢查、diff 檢查）─▶ 直接推 main

提案
  各 Agent ─追加一行─▶ correction-queue.jsonl ─▶ 主 Session 逐條 y/n/edit ─▶ 合入教訓檔 ─▶ 清空佇列
                                                       └─ 其餘流程（雜湊、閘門、推送）不變
```

## 2. 與既有流程的衝突點

| # | 既有規則（出處：該倉庫的文件） | 佇列放在倉庫內時的衝突 | 嚴重度 |
|---|---|---|---|
| C1 | 共用協作規則第 4 條：「SSOT 改動先形成 diff，不讓 consumer 自動自我改寫共享資產」；SSOT 契約資料責任表：共用規則與知識的**唯一寫入權威是「經審查的提交」** | 佇列要讓各 consumer Agent **直接寫進該倉庫**。即使只是追加到佇列檔，也是 consumer 自行寫入共享倉庫；與「先形成 diff、再審查」的順序相反（佇列檔在審查前就已落地、可能被別人 pull 到） | 高 |
| C2 | `verify_repo.py` 的檢查範圍：只對 `.md/.json/.yaml/.yml/.py/.ps1/.sh` 做 UTF-8、密碼樣式、斷連結、`.md` 的中性用詞檢查（讀碼：非這些副檔名直接 `continue`） | `.jsonl` **不在掃描範圍**：佇列裡的自由文字（`scene` 常含對話情境、本機路徑、暱稱）可能繞過密碼掃描與中性用詞規則，直接躺在私有倉庫的歷史裡 | 高（可用擴充掃描器修正，但要改倉庫程式與補測試） |
| C3 | 收錄流程「不收」清單：憑證、帳號、聯絡資訊、單一 repo 專屬規則、只對某個 Agent 成立的機制；操作手冊「寫進 repo 的文字用中性詞，稱使用者」 | 會話糾正本質上大量是個人化、單一 Agent 的內容（語氣、稱呼、某工具的行為）。佇列若沒有「共用／專屬」的分流欄位，會把這些東西大量堆進共用倉庫，再靠審核人逐條剔除，反而增加審核量 | 中 |
| C4 | 共用協作規則第 10 條：不得把同一份 HANDOFF 寫成跨專案共用工作佇列 | 精神相同：共用倉庫裡的單一佇列檔容易變成跨專案、跨 Agent 的雜物堆。規則本身針對 HANDOFF，不是對糾正佇列的直接禁令，所以列為「風險」而非「牴觸」 | 低 |
| C5 | 操作手冊「每一項都要遵守」：確認沒有其他 session 在寫同一批檔案；倉庫採**直接推 main、不開 PR** | 多個 Agent 同時對**同一個檔案尾端**追加，會在 Git 層產生衝突（兩邊都在檔尾新增行）。目前流程靠「先確認沒人在寫」規避；佇列的設計前提正好是「多方同時寫」，兩者互斥 | 中 |
| C6 | 登記簿 `sharedDocuments` 以整檔 SHA-256 當漂移偵測，檔案內容變動就把狀態改回 `candidate-review-pending` | 佇列若登記進去，每追加一行就漂移一次；不登記則沒有任何完整性檢查。兩邊都不理想 | 中 |

沒有衝突的部分：`lessons.md` 的格式（每條附來源與日期）、技能登記、備份與部署機制，佇列都不會碰。

## 3. 問題是否真的存在：可量測的證據

2026-10-26 以 `git log` 統計該倉庫（唯讀）：

| 指標 | 數值 | 意義 |
|---|---|---|
| 倉庫提交總數 | 12（2026-10-24 起） | 倉庫很新、變動少 |
| 合併提交（merge commit） | 0 | 沒有出現過分支合併；**沒有發生過需要人工解的並行寫入衝突的紀錄** |
| 觸碰教訓檔的提交 | 5（含 2026-10-24 初始提交；其餘 4 筆在 2026-10-25～26） | 近兩天約每天 2 次 |
| 教訓檔規模 | 約 28 KB（27,961 bytes）、9 個章節 | 尚在可整檔審閱的大小 |
| 提交作者 | 全部為同一個 git 使用者名 | **無法由 git 歷史判斷是哪個 Agent 寫的**；只能從提交訊息裡的 Agent 名稱推測（例如訊息寫明記錄的是某 Agent 的機制） |

限制：這些數字只能說「**目前沒有看到**並行覆蓋或規則被改壞的跡象」，不能證明沒有發生過（例如某 Agent 的修改被後來的提交覆蓋，歷史裡看不出來）。另外，倉庫才運作 3 天，樣本很短。

## 4. 既有流程其實已提供等效的審核

操作手冊第 1 項已規定：

- 每條知識結尾註明來源與日期，「只寫來源有的內容，不擴大、不刪但書」；
- 大量內容「先用子 agent 只讀分類，主對話審核後寫入，再交全新 context 的審查比對原檔」——這就是「先分類排隊、主 Session 審核、再合入」的人工版；2026-10-23 的驗收清單記載了一次實際執行：一批記憶先分類成事實／偏好／教訓，再由全新 context 比對原檔並修正 9 處後通過；
- 改動後必須更新文件雜湊，登記簿狀態自動回到 `candidate-review-pending`（`verify_repo.py --update-hashes`），所有共用文件目前都是這個狀態（2026-10-26 讀登記簿：6 份共用文件，全數 `candidate-review-pending`、`runtimeDiscoveryVerified: false`）。

**真正缺的一塊**：這個審核旗標是**整檔粒度**，沒有「逐條」的 y／n／edit 紀錄；而且目前所有文件都停在待審，表示旗標只是標記，不是會被清掉的佇列。佇列能補的正是這個粒度，但這是「審核紀錄」問題，不是「並行寫入」問題，用別的方式也能解（第 5 節）。

## 5. 替代方案比較

| 方案 | 做法 | 優點 | 缺點 | 判定 |
|---|---|---|---|---|
| A 維持現狀 | 照操作手冊第 1 項 | 零改動；沒有新機制要維護；符合現有規則 | 沒有逐條審核紀錄 | **現階段採用** |
| B 倉庫內佇列 | `knowledge/` 下加 `correction-queue.jsonl`（範本原樣） | 與範本一致 | 見第 2 節 C1、C2、C5、C6 | 不採用 |
| C 倉庫外本機佇列 | 佇列放在倉庫外的本機私有資料夾（操作手冊本來就規定備份、紀錄、試驗物件放 `C:\AgentData`），不進 Git；主 Session 審核後依操作手冊第 1 項寫入教訓檔 | 避開 C1（尚未成為共享資產）、C5（不經 Git，不衝突）、C6；佇列本身不被推到遠端 | 要新增一個本機路徑約定與一支追加／審核小工具；多台機器各有各的佇列；`.jsonl` 若不進倉庫則不需擴充 `verify_repo.py`，但審核後寫進 `.md` 的內容仍照現有掃描 | **觸發條件命中時再做** |
| D 把「逐條審核」記在 PR | 改成每次教訓更新開 PR，用 PR 審查當佇列 | 平台原生審查、可留紀錄 | 該倉庫明確規定直接推 main、不開 PR；改變流程成本最高 | 不採用 |

## 6. 若日後啟動方案 C：資料綱要與審核規則

### 6.1 JSONL 欄位（以範本欄位為底，針對該倉庫的規則調整）

| 欄位 | 型別 | 必填 | 說明 |
|---|---|---|---|
| `id` | string | 是 | `corr-<UTC 時間戳>-<序號>`，佇列內唯一 |
| `ts` | string | 是 | ISO 8601 含時區 |
| `by` | string | 是 | 提出的 Agent 名稱（因為 git 作者無法區分，這個欄位是唯一的歸屬依據） |
| `scope` | enum | 是 | `shared`（跨 Agent 共用）／`agent-specific`（只對某 Agent 成立）。`agent-specific` 一律退回該 Agent 的原生記憶，**不進共用倉庫**（對應收錄流程「不收」清單） |
| `scene` | string | 是 | 發生什麼；**提交前先去敏**（不寫對話原文、聯絡人、本機路徑；對應 C2、C3） |
| `wrong` | string | 是 | 錯在哪 |
| `correct` | string | 是 | 該怎麼做 |
| `source` | string | 是 | 證據來源與日期（對應「每條結尾註明來源與日期」）；沒有來源不得入佇列 |
| `category` | enum | 否 | 沿用範本：`verification｜approval｜language｜persona｜tone｜factcheck`；`persona`、`tone` 通常是 `agent-specific` |
| `status` | enum | 是 | `pending`／`accepted`／`rejected`／`edited` |
| `reviewed_at`、`review_note` | string | 審核後必填 | 審核日期與一句話理由；`rejected` 必須有理由，避免同一條反覆被提 |

### 6.2 審核規則

1. 只有主 Session 能把 `accepted`／`edited` 的內容寫入共用教訓檔；其他 Agent 只能追加 `pending`。
2. 合入時照操作手冊第 1 項走完雜湊更新與推送閘門，**佇列不進 Git**。
3. 動態資料（模型名、價格、額度、版本）合入時一定帶日期；沒有日期退回。
4. `scope: agent-specific` 與含個資的項目直接 `rejected`，不討論。
5. 已存在相同教訓時標 `rejected` 並指向既有章節（去重）。

## 7. 重新評估的觸發條件

任何一條成立就重新開這份評估（數字是本文建議的起始值，不是量測出的定論）：

| 觸發 | 如何偵測 |
|---|---|
| 同一天有兩個以上 Agent 修改教訓檔並出現實際衝突或後者覆蓋前者 | `git log` 出現教訓檔的 revert／衝突解決提交，或維護者回報 |
| 教訓檔的更新提交每週超過約 10 次，或檔案超過約 100 KB | `git log --since` 計數與檔案大小 |
| 出現「被審核通過後才發現是 Agent 專屬或含個資」的案例 | 事後審查 |
| 該倉庫改為多人（非單一維護者）協作 | 協作者名單變動 |
