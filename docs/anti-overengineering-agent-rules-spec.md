# AI Coding Agent 防過度設計與防官僚化精實工程手冊（8 條白話規約與反模式清單）

本手冊提煉自台灣科技投資人「麥克風」發布之給 AI Agent 的 8 條極簡工作規約，旨在根治 AI Coding Agent（如 Codex、Claude Code、Cursor、Antigravity）在日常軟體開發中的「過度設計毛病」、「假環境測試」、「無休止審查迴圈」與「規約通膨」。

---

## 1. 核心白話 8 條規約速查表

| 編號 | 白話規約 | 工程原則 | 攔截的典型反模式 |
| :---: | :--- | :--- | :--- |
| **1** | **先真的跑通一次，假環境的測試不算數** | Target-Env Verification | Mock 狂魔、自我催眠假綠燈、不跑真實直譯器 |
| **2** | **先做最簡單的版本，預計超過 300 行要先說明理由** | KISS / Line Budget | 過早抽象、過度封裝、動輒引入 5 層設計模式 |
| **3** | **審查最多兩輪，之後只擋「跑不完」或「會壞資料」的問題** | Bounded Review / Liveness First | 審查死迴圈（Doom Loop）、無限挑剔排版與命名品味 |
| **4** | **偶爾重複、偶爾要人補救都可以接受，不追求完美** | Pragmatic Duplication | 過早 DRY、為了消除 3 行重複代碼發明複雜泛型 |
| **5** | **改了能復原的事不用審批，只有刪資料、動錢、對外發布、改權限才要** | Two-way vs One-way Doors | 芝麻綠豆事事請示人類、中斷使用者心流 |
| **6** | **想加新規則或新關卡要你同意，還要說明能不能順便刪掉一條舊的** | Zero Rule Growth / Sunset | 規則只增不減、上下文被互相衝突的規約塞爆 |
| **7** | **同一個原因卡兩次就停下來，用三句白話問你，不要再加機制繞過去** | Fail Fast, Speak Plainly | 遇到錯誤自己寫 Wrapper 或 Eval 越繞越亂 |
| **8** | **回報只講做了什麼、你怎麼親眼看到結果、下一步是什麼，不貼 hash 和術語** | Lean Reporting | 結案貼一堆 Commit SHA、Base64 或官僚公文腔 |

## 2. 深度執行守則

### 2.1 規則 1：破除假環境測試（Real-Process Mandate）
- **判定標準**：在 Windows 11 原生環境中，必須調用真實的 `python`、`rustc`、`node`、`git` 進程。
- **禁止清單**：
  - 嚴禁透過 Monkey-patch 將會失敗的 I/O 直接替換為永遠回傳 True 的 Dummy。
  - 嚴禁為了讓測試通過而註解掉斷言（Assertion）或使用 `try: ... except: pass` 吞掉例外。
  - 嚴禁在未執行任何命令的情況下直接宣稱「所有測試已通過」。

### 2.2 規則 2：300 行實作預算制（The 300-Line Budget Rule）
- **核心理念**：簡單的程式碼容易被人類理解、審查與重構；龐大的單元只會製造未知 Bug。
- **實踐規約**：
  - 任何單一功能、修復或模組新增，目標行數應在 300 行以內。
  - 若評估必須超過 300 行，Agent 必須在計畫或開工前明確給出理由（例如：第三方協議結構定義、包含完整單元測試或靜態 Schema 映射）。

### 2.3 規則 3：兩輪審查熔斷機制（Two-Round Review Cap）
- **審查輪次定義**：
  - **Round 1（全面審查）**：檢查邏輯正確性、安全性、規格相符度與邊界條件。
  - **Round 2（修復驗證）**：僅驗證 Round 1 指出的問題是否修復，嚴禁提出全新的風格或主觀命名異議。
  - **Round 3+（熔斷放行）**：若第二輪後仍有爭議，代理人只准攔截兩類問題：
    1. **程式跑不完（Liveness Failure）**：無窮迴圈、死鎖（Deadlock）、記憶體洩漏。
    2. **資料損壞與資安威脅（Safety Failure）**：刪除正式資料、SQL Injection、未授權外洩。
    其餘程式碼品味與微小優化一律記錄為後續觀察，不得阻擋交付。

### 2.4 規則 5：單向門 vs 雙向門操作矩陣（One-Way vs Two-Way Doors）

```
+---------------------------------------------------------------------------------+
|                                 操作決策矩陣                                    |
+---------------------------------------------------------------------------------+
|  雙向門 (Two-Way Door) - 自主推進，不主動打擾:                                   |
|  - 本地代碼編輯、重構與新增檔案 (隨時可 git checkout / git revert)              |
|  - 跑測試、建置、靜態分析、查看日誌與排查 Bug                                   |
|  - 建立本地暫存分支、寫測試用例、更新內部文件                                   |
+---------------------------------------------------------------------------------+
|  單向門 (One-Way Door) - 必須暫停並明確向人類請求確認:                           |
|  - 刪除遠端資料庫、清空生產磁碟或執行 DROP TABLE / rm -rf                       |
|  - 涉及金錢扣款、API 付費升級或訂閱變更                                         |
|  - 向公共上游 (Upstream) 提交 PR、公開推送到主倉庫或發布 Release 產物            |
|  - 修改生產環境防火牆、變更 IAM 金鑰或授予全域管理員權限                        |
+---------------------------------------------------------------------------------+
```

### 2.5 規則 6：規則淨零增長法（Rule Sunset Protocol）
- 每當團隊想要在 `CLAUDE.md`、`AGENTS.md` 或 `GEMINI.md` 新增一條規約時，必須同時回答：
  > 「這條新規則是否能取代某條舊規則？如果不能，是否有過期的規則可以順便刪除？」
- 維護規則庫不是堆疊廢話，而是雕刻核心原則。過多的規則會導致 LLM 上下文衰減與指令遵循度下降。

### 2.6 規則 7：撞牆兩次立即停下（Two-Strike Fail-Fast）
- 當一個錯誤連續發生 2 次（例如指令路徑不對、權限拒絕、依賴缺失）：
  - **嚴禁**：再寫一支包裝腳本假裝解決、嘗試第三種複雜的繞道 Hack。
  - **必須**：立即中斷，並使用不超過 3 句白話向使用者說明：
    1. 目標是什麼。
    2. 真正卡住的原因是什麼。
    3. 需要使用者提供什麼決定或授權。

### 2.7 規則 8：三段式清爽回報（Lean Reporting Format）
結案回報一律遵循以下三大結構，不廢話、不充數：
1. **做了什麼**：一句話講完改動重點與受影響檔案。
2. **如何親眼驗證**：提供一條具體指令或瀏覽動作，讓人類能一眼驗證成果。
3. **下一步是什麼**：指出後續最自然的推進動作（若無則寫無）。
